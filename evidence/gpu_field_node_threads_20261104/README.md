# GPU 声场：每个积分点一个线程的试验（2026-11-04）

> **状态（2026-11-09 核对）：** 现行。按点数自动选择计算核心；2026-11-09 起方片用同样的规则（`evidence/y_channel_chip_20261109/`）。

用户要求试验"每个积分点各用一个线程（4 个圆片 × 点数 × 96 个线程，最后再求和）"，并与现在的计算核心比较速度。**只是试验，工程代码没有改。**

`EXPLORATORY / PRETRAIN_TIER / training_ready=false`。RTX 4060 Laptop GPU，Warp 1.18.0，2.5 MHz，96 个积分点。

## 做法

- **现在**（`microbubble/_warp_discs.py` 的 `fnm_discs`）：一个线程负责"一个圆片 × 一个点"，依次算完 96 个积分点。
- **试验**（`NODE_THREADS_SCRIPT.py.txt` 的 `fnm_discs_node_threads`）：用 `wp.launch_tiled` 给每个"圆片 × 点"分一个 96 线程的块，每个线程算一个积分点的贡献，再用 `wp.tile_sum` 在块内按固定顺序求和。每个积分点的算式与现在循环里的一轮相同。
- 整条运行的对比方法：把 `gpu.GPUWaterDiscs` 临时换成试验版本，配置为实验式三段的第一段，32 泡跑 0.5 s、128 泡跑 0.3 s，每种各跑 2 次。

## 结果（`node_threads_speed.png`、`NODE_THREADS.json`）

| 每次调用的点数 | 计算本身：现在 → 试验 | 整次调用（含拷贝）：现在 → 试验 |
|---|---|---|
| 32 | 0.451 → 0.079 ms（快 5.7 倍） | 0.709 → 0.360 ms（快 2.0 倍） |
| 128 | 0.729 → 0.164 ms（快 4.4 倍） | 1.08 → 0.51 ms（快 2.1 倍） |
| 1024 | 0.735 → 0.938 ms（慢） | 1.22 → 1.44 ms（慢） |
| 16,384 | 7.93 → 14.5 ms（慢约一倍） | 11.4 → 17.7 ms |
| 131,072 | 57.9 → 110 ms（慢约一倍） | 81.2 → 134 ms |

- **结果一致，而且可以逐位复现**：与现在的 GPU 结果相差 ≤1.3e-15，与 CPU 相差 ≤8e-15。同一输入算两次，结果逐位相同。整条运行的步数与 CPU 相同，最终位置与 CPU 相差 ≤1.5e-17 m。
- **整条运行**（2 次的中位数，含 GPU 初始化约 0.5 s）：
  - 32 泡：CPU 4.6 s、现在的 GPU 6.2 s、试验版 4.6 s；
  - 128 泡：CPU 5.7 s、现在的 GPU 7.1 s、试验版 5.8 s。

  试验版不再比 CPU 慢，但也没有更快。原因是声场只占每一步的一小部分，其余的振动、力和接触计算都在 CPU 上；短运行里 GPU 初始化也占了约一成。
- **点多时变慢的原因**：96 个线程各自都重算一遍这个点的几何量和 e^(−ikz)（一次 cos 和一次 sin），而现在的写法每个点只算一次；块内求和也有额外开销。点多时显卡本来就已经占满，这部分多出来的运算就直接体现成用时。
- 试验版的计算核心第一次编译用了约 1.4 s。

## 补充：每个点的几何量和 e^(−ikz) 只在块里算一次（同日）

用户要求测试这一改进的速度收益。脚本 `NODE_THREADS_SHARED_SCRIPT.py.txt`，结果 `NODE_THREADS_SHARED.json`、`node_threads_shared_speed.png`。

- **V1**：上面的试验版，每个线程都重算几何量和 e^(−ikz)。
- **V2**：e^(−ikz) 每个块只算一次。它在三个求和式里都是线性出现的，所以 96 个线程只求不含它的和，最后由 0 号线程乘上一次。
- **V3**：在 V2 的基础上，几何量（z、r）只由 0 号线程算一次，再通过块内共享内存分给其余线程。

只计计算本身（毫秒）：

| 点数 | 现在的循环版 | V1 | V2 | V3 |
|---|---|---|---|---|
| 32 | 0.437 | 0.072 | 0.075 | 0.073 |
| 128 | 0.749 | 0.162 | 0.151 | 0.143 |
| 1024 | 0.725 | 0.922 | 0.892 | 0.833 |
| 16,384 | 7.92 | 14.5 | 13.7 | 12.7 |
| 131,072 | 60.1 | 113.6 | 110.3 | 100.6 |

- **收益很小**：点多时 V2 比 V1 快约 3–5%，V3 快约 10–12%，仍比现在的循环版慢 1.6–1.7 倍；点少时三者没有差别。所以点多时变慢的主要原因不是重复计算。剩下的差距可能来自块内求和（每个线程把 6–8 个数写进共享内存、多次同步）以及每块占用共享内存导致同时运行的线程变少，这一点**没有实测确认**。
- **结果一致**：三个版本与现在的 GPU 结果相差 ≤1.3e-15，与 CPU 相差 ≤8.4e-15，重复计算逐位相同。
- **整条运行**（2 次的中位数）：
  - 32 泡 0.5 s：CPU 5.3 s，现在 5.7 s，V1 4.9 s，V2 5.0 s，V3 5.1 s；
  - 128 泡 0.3 s：CPU 6.0 s，现在 7.2 s，V1 6.2 s，V2 6.1 s，V3 6.5 s。

  三个试验版之间的差别小于两次重复之间的波动（约 ±0.5 s）。

## 采用：按点数自动选择计算核心（同日）

用户确认采用"按点数自动选择核心"，并要求不改动已有的分行和代码注释（已有内容只追加，不改写）。

- `microbubble/_warp_discs.py` 末尾新增 `fnm_discs_node_threads`，即上面的 V1。
- `microbubble/gpu.py` 新增 `NODE_THREAD_MAX_POINTS = 512`。`GPUWaterDiscs.evaluate` 在点数不超过它时用新核心，否则用原来的 `fnm_discs`。已有的 `wp.launch(...)` 调用只改了核心名和 `dim`，并加了一行 `block_dim`。
- **分界点**（`AUTO_KERNEL.json`，整次调用）：两种核心在约 700 个点处交叉，96 和 192 个积分点都一样。512 个点时新核心快 1.2–1.6 倍，取 512 留出余量。
- **整次调用**（2.5 MHz）：32 个点时 GPU 0.34 ms，CPU 0.66 ms；128 个点时 0.46 ms 对 2.2 ms；16,384 个点时 11 ms 对 554 ms。
- **整条运行**（`AUTO_RUNS.json`，结果在 `results/pretrain_gpu_field_auto/`；与之前的 `results/pretrain_gpu_field/` 条件相同，CPU、GPU 两条同时运行）：

  | 运行 | CPU | GPU，只用循环版 | GPU，自动选择 |
  |---|---|---|---|
  | 实验式 32 泡 4.5 s | 32.0 s | 40.6 s | 32.0 s |
  | 实验式 128 泡 4.5 s | 85.1 s | 94.7 s | 87.9 s |
  | 随机动作 32 泡 2 s | 22.7 s | 30.1 s | 23.4 s |

  步数与 CPU 相同，泡位置最大差 1.6e-17、8.0e-20、1.5e-18 m。CPU 运行与之前逐位相同；两次之间 CPU 用时相差 5–8%，属于正常波动。
- **测试**：55 项全部通过。`tests/test_model.py` 新增 64 个点（走新核心）与 CPU 的对比，限值仍为 1e-12。
- 自动选择后，GPU 的结果与之前只用循环版时相差约 1e-15，所以以前的 GPU 运行不能逐位复现；CPU 的 `direct` 和 `cache` 不受影响。
